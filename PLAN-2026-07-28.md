Implementing the 2026-07-28 specification requires an architectural sequence where schema, transport headers, stateless execution, multi round-trip mechanics, and higher-level extensions build on each other without breaking backward compatibility:

### Phase Ordering Rationale

1. **Phase 1 (Foundations & Schema Non-Breaking Additions)**:
   - Contains zero behavioral breakages.
   - PRs [#1064](https://github.com/modelcontextprotocol/java-sdk/pull/1064), [#1037](https://github.com/modelcontextprotocol/java-sdk/pull/1037), [#1053](https://github.com/modelcontextprotocol/java-sdk/pull/1053), and [#1062](https://github.com/modelcontextprotocol/java-sdk/pull/1062) can land immediately with minor adjustments.
   - Adds `ProtocolVersions.MCP_2026_07_28 = "2026-07-28"`.

2. **Phase 2 (Transport Headers & Server Discovery)**:
   - Streamable HTTP transports must emit `Mcp-Method` on every POST request and `Mcp-Name` on tool/resource/prompt requests.
   - Introduce `server/discover` endpoint and request/response models.
   - Allows clients to discover 2026-07-28 server capabilities without performing a stateful `initialize` handshake.

3. **Phase 3 (Stateless Transport Rework & State Handles - Multi-Week Core Effort)**:
   - SEP-2575 & SEP-2567 eliminate `Mcp-Session-Id` header requirements.
   - `_meta` field handling: every JSON-RPC request params may include `_meta: { clientInfo, capabilities, protocolVersion, stateHandle }`.
   - Migrate existing [McpStatelessAsyncServer.java](file:///Users/slachiewicz/oss/mcp-java-sdk/mcp-core/src/main/java/io/modelcontextprotocol/server/McpStatelessAsyncServer.java) from simulating 2025-11-25 initialize to natively serving single-turn stateless requests.

4. **Phase 4 (MRTR - Multi Round-Trip Requests)**:
   - Implement SEP-2322: tool executions requiring human or user input return `resultType: "input_required"`, containing `requestState` and an elicitation prompt or schema.
   - Client resumes execution by calling `tools/call` with matching `requestState`.
   - Requires non-blocking reactive API design in Reactor/WebFlux and synchronous MVC wrappers.

5. **Phase 5 (Official Spec Extensions)**:
   - Provide standard implementations of `Tasks` (SEP-2663) and `MCP Apps` (SEP-1865) leveraging the new Extensions framework and MRTR primitives.

## 3. Backward Compatibility & Dual-Spec Negotiation Strategy

### Architectural Choice: Dual-Protocol Server Handlers vs Transport Flags

We evaluated two architectural patterns across reference SDKs:
1. **The Python / Cloudflare Approach (Unified Dual-Stack Server Handler)**:
   - A single server endpoint accepts both legacy 2025-11-25 clients (which initiate via `initialize` handshake and supply `Mcp-Session-Id`) and 2026-07-28 clients (which query `server/discover` or send direct stateless requests with `_meta`).
2. **The Go / TypeScript Approach (Transport-Level Stateless Mode Flag)**:
   - Explicit builder configuration (e.g. `HttpServerTransportOptions.stateless(true)`).

### Recommendation: Unified Dynamic Dual-Stack with Opt-In Strict Mode

**Rationale**:
- In Java enterprise deployments (Spring Boot, Quarkus, Tomcat), servers are deployed as long-lived endpoints behind reverse proxies. Forcing separate endpoints or ports for 2025-11-25 and 2026-07-28 creates significant deployment friction.
- **Incoming Request Resolution Protocol**:
  1. If request method is `server/discover` or `MCP-Protocol-Version: 2026-07-28` is present without an active session: handle via stateless protocol pipeline.
  2. If request method is `initialize`: allocate session / route to legacy stateful handshake pipeline.
  3. If request contains `Mcp-Session-Id`: look up session context (2025-11-25 mode).
  4. If request has no session ID and is not `initialize`: check for `_meta` in params. If present, evaluate statelessly (2026-07-28 mode).

### Public API Breaking Change Audit: 2.x Minor vs 3.0 Major

- **2.x Minor Target**:
  - `McpSchema` records: Add new constructor overloads marked `@Deprecated` for backwards binary compatibility, preserve existing fields, use `@JsonInclude(NON_ABSENT)`.
  - `ClientCapabilities` / `ServerCapabilities`: `extensions` and new sub-capabilities are optional (`null` allowed).
  - Deprecations for Roots, Sampling, Logging emit standard compiler warnings but remain 100% operational.
- **What would force 3.0**:
  - Deletion of `McpServerSession` or removing `initialize()` from `McpClient`.
  - Changing return types of `McpAsyncClient.callTool(...)` from `Mono<CallToolResult>` to a wrapper for MRTR.
- **Recommended 2.x Solution**:
  - Introduce `McpAsyncClient.callToolMultiRoundTrip(...)` or handle MRTR resolution seamlessly inside existing client methods when a continuation handler is supplied, keeping 2.x binary compatibility intact.

## 6. Risks, Technical Decisions & Draft Maintainer Comment

### Critical Technical Decisions

1. **Reactor/WebFlux vs Virtual Threads for MRTR & Stateless Handlers**:
   - Reactor `Mono`/`Flux` is the reactive foundation of `mcp-core`. MRTR requires pausing and resuming execution across HTTP round trips.
   - *Decision*: In `McpStatelessAsyncServer`, state must be explicitly returned in `CallToolResult.requestState` rather than holding an open thread or suspended Mono.
2. **Jackson 2 vs Jackson 3 `_meta` Handling**:
   - `_meta` fields in JSON-RPC can contain open-ended nested JSON maps.
   - *Decision*: Abstract `_meta` parsing using `McpJsonMapper` with `TypeRef<Map<String, Object>>` to guarantee identical behavior across `mcp-json-jackson2` and `mcp-json-jackson3`.
3. **Spring AI Ecosystem Alignment**:
   - `spring-ai-mcp` consumes `mcp-core` client and server abstractions.
   - *Decision*: Keep `McpSyncClient` / `McpAsyncClient` method signatures backward compatible to prevent breaking downstream Spring AI tool calling integrations.
